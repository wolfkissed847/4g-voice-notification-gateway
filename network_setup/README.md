# Network Architecture — LAN หลัก + 4G สำรอง

## แนวคิด

Raspberry Pi ในโปรเจคนี้ใช้ **อินเทอร์เน็ตจาก LAN ออฟฟิศเป็นหลัก** (dashboard, gTTS API, NTP ฯลฯ)
และ **สลับไปใช้ 4G จากโมดูล A7670C อัตโนมัติเมื่อ LAN หลุด** — เพื่อให้ระบบยังทำงานต่อได้แม้ในสถานการณ์
ที่ตั้งใจให้ตรวจจับ เช่น **ไฟดับ** (ซึ่งมักทำให้ router/switch ในออฟฟิศดับไปด้วย)

**สิ่งสำคัญที่ต้องแยกให้ชัด:**

| ช่องทาง | ใช้ทำอะไร | ขึ้นกับ LAN/4G ไหม |
|---|---|---|
| เสียง (โทรออกแจ้งเตือน) | AT command (`ATD`) ผ่านซิมโดยตรง | **ไม่ขึ้นกับ LAN/4G data เลย** — ใช้สัญญาณเสียงของซิมเสมอ |
| อินเทอร์เน็ต | Dashboard, เรียก gTTS API, NTP sync | LAN เป็นหลัก, 4G เป็น fallback |

ดังนั้นแม้ LAN และ 4G data จะล่มพร้อมกันทั้งคู่ **ระบบยังโทรแจ้งเตือนได้** (แค่ dashboard เข้าไม่ได้ชั่วคราว
และถ้า audio cache ของข้อความนั้นยังไม่เคย generate มาก่อน อาจโทรไม่ได้เพราะสร้างไฟล์เสียงไม่ได้ —
ดู "ข้อจำกัดที่ควรรู้" ด้านล่าง)

## วิธีติดตั้ง

1. เชื่อมต่อโมดูล A7670C เข้ากับ Pi (ผ่าน USB ตามที่ตั้งค่าไว้ใน `.env`)
2. แก้ APN ในไฟล์ `setup_network_failover.sh` ให้ตรงกับผู้ให้บริการ (เช่น GOMO ใช้ AIS)
3. รัน:
   ```bash
   sudo bash network_setup/setup_network_failover.sh
   ```
4. ทดสอบ: ถอดสาย LAN ออก แล้วเช็คว่า Pi สลับไปใช้ 4G เองไหม
   ```bash
   nmcli device status
   ```

## หลักการทำงาน

NetworkManager (default บน Raspberry Pi OS Bookworm ขึ้นไป) เลือก default route จาก
connection ที่ `autoconnect-priority` สูงสุดที่ **เชื่อมต่อได้จริง ณ ขณะนั้น**:

- LAN priority = 100 (สูงสุด — ใช้ก่อนเสมอถ้ามีสายและเน็ตใช้ได้)
- 4G priority = 10 (ใช้ต่อเมื่อ LAN หลุดหรือไม่มีสาย)

เมื่อ LAN กลับมาใช้ได้ NetworkManager จะสลับ default route กลับไปที่ LAN เองเช่นกัน
**ฝั่งโค้ด Python (FastAPI/gTTS) ไม่ต้องรู้เรื่องนี้เลย** เพราะเรียกผ่าน HTTP client ปกติ
ซึ่งใช้ default route ของ OS อยู่แล้ว

## ข้อจำกัดที่ควรรู้ (ต้อง verify กับฮาร์ดแวร์จริง)

- **AT command channel (โทร) กับ data channel (internet) พร้อมกัน**: A7670C ปกติแบ่ง virtual
  serial port หลายพอร์ตผ่าน USB (เช่น AT command กับ PPP data คนละพอร์ต) แต่ต้องทดสอบจริงว่า
  ตอนกำลังคุยสาย (voice call) ยังใช้ 4G data พร้อมกันได้ไหม — ขึ้นกับว่าเป็น VoLTE (เสียง+data พร้อมกันได้)
  หรือ CSFB (สลับไปโหมด 2G/3G ตอนคุยสาย ซึ่งจะทำให้ data หลุดชั่วคราว)
- **ความหน่วงตอนสลับ**: การสลับ default route ใช้เวลาสองสามวินาที ระหว่างนั้น request ที่ค้างอยู่
  (เช่นเรียก gTTS) อาจ timeout ได้ — แนะนำให้ตั้ง retry ที่ฝั่ง `tts_service.py` เผื่อไว้
- **Audio cache**: เนื่องจาก `text_to_speech()` cache ไฟล์เสียงตาม hash ของข้อความ ถ้าข้อความแจ้งเตือน
  นั้น**เคย generate มาก่อนแล้ว** (มีไฟล์ใน `audio_cache/`) ระบบจะเล่นเสียงได้ทันทีแม้ไม่มีอินเทอร์เน็ตเลย
  แต่ถ้าเป็นข้อความใหม่ที่ไม่เคย generate มาก่อน และไม่มีทั้ง LAN และ 4G data พร้อมกัน จะสร้างไฟล์เสียงไม่ได้
  — **แนวทางแก้**: เตรียม generate ข้อความแจ้งเตือนที่คาดว่าจะใช้บ่อย (เช่น "เซิร์ฟเวอร์หลักล่ม", "ไฟดับ")
  ไว้ล่วงหน้าใน `audio_cache/` ตั้งแต่ตอน setup ระบบ
